# Orchestra-Multi-AI：让多个 AI 助手分工协作

> 通用版技能仓库 · A generic skill for multi-assistant collaboration
>
> 本仓库放通用技能与可配置模型工具，不含任何人的助手名单、项目、账号或密钥。个人配置放在你自己的私有仓库，不进本仓库。

## 项目是什么（What This Is）

给「一个人用好几个 AI 助手、跨多个项目干活」准备的技能：每个角色负责什么、活怎么派、什么活用哪个模型、出错怎么办，以及改这些规矩的流程。

- **仓库就是技能。** 技能是一个文件夹，里面的 `SKILL.md` 是说明书，写明什么时候读、读了怎么做。整个文件夹放进助手能读到的技能目录，命名 `orchestra` 就能用。
- **分两层。** 通用的角色、流程、模板谁都能用；助手名单、项目、模型配置等个人内容另放私有仓库，不进本仓库。
- **职责边界。** 项目仓库只写本项目的开发方法；助手之间怎么分工、派工，放本技能仓库。
- **只改正本，再同步。** 本仓库的 `main` 是通用部分的正本；本机技能目录、模型调用程序（替助手调你的模型并记账的小程序）读取的规则表、各助手的线上设定都是抄本，只从正本复制。
- **四条底线。** 复审不用作者用过的那家模型；不合并自己的改动；改规矩走流程；密钥不进任何文件。

### 仓库结构（Repository Layout）

```
Orchestra-Multi-AI/         # 通用仓库；装到本机后文件夹名为 orchestra/
├─ SKILL.md                 # 入口，一页纸：何时读、读了怎么做
├─ README.md                # 给人看：是什么、怎么装
├─ CHANGELOG.md             # 改动记录和版本号
├─ roles/                   # 各角色职责、禁止事项、设定模板，外加全员规矩块
├─ routing/                 # 规则表格式说明＋空白模板
├─ process/                 # 派工、交接、复审、合并、改规矩、同步，每个流程一份
├─ examples/                # 虚构团队，演示 config/ 怎么填
├─ scripts/                 # 模型调用、估时、运行核对工具及说明
└─ .github/                 # 自动检查（CI）设置
```

你的个人配置（助手名单、规则表、项目清单、各助手设定全文、禁用词）放在你自己的私有仓库，装到本机同一文件夹下的 `config/`，不进本仓库；照 `examples/` 填。

```
config/                      # 私有配置仓库内；装到本机 orchestra/config/
├─ team.json                 # 助手名单：名字、角色、能用哪些引擎
├─ rules.json                # 真实规则表
├─ projects.md               # 项目清单
├─ CHANGELOG.md              # 配置的改动记录和版本号（助手报的是这个号）
├─ profiles/                 # 各助手设定全文（线上设定的正本）
└─ private-words.txt         # 禁用词：你的名字、助手名、项目名、账号名、私有仓库名
```

配置版本号取自配置仓库的 `CHANGELOG.md`。

注：`.json` 是程序能直接读的表格文本；引擎指某一家的模型（如 Claude、Codex、DeepSeek）。角色只写通用的：调度、开发、复审、调研、平台对接、审批、用量、配置管理。

- **规则表格式和同步脚本由开发角色维护。** 规则表格式由开发角色在路由规则表任务里定，定了再把格式说明和空白模板放进 `routing/`（这里不另起一套），空白模板中的引擎使用占位符，由使用者填写；同步脚本（把正本复制到各处的小程序）也由开发角色写。

### SKILL.md 做什么（The Skill Entry）

`SKILL.md` 只写一页，开头写明何时读；正文写五步用法，并把四条底线（复审不用作者用过的那家模型、不合并自己的改动、改规矩走流程、密钥不进任何文件）写进入口：

1. 读 `config/team.json`，找到你的角色；没有 `config/` 就停下，请使用者先配置，不要猜。
2. 读 `roles/<你的角色>.md`，照里面的职责和禁止事项做。
3. 调模型前查 `config/rules.json`：什么活用哪个引擎、什么强度、失败怎么办；引擎名以表为准。
4. 派活、交接、复审、合并，照 `process/` 里的流程。
5. 要改规矩，别直接改文件，照 `process/change-rules.md` 提。

## 快速安装（Quick Install）

1. 整个文件夹放进助手能读到的技能目录，命名 `orchestra`。
2. 把你的私有配置仓库放到同一文件夹下的 `config/`；可以以 `examples/` 为起点，改成你自己的。
3. 运行 `scripts/check.sh`，全部通过再用。
4. 每个助手的设定里加一句：开工前先读技能 `orchestra`。
5. 冒烟测试：跑一次最简单的试用，确认助手真会读技能；让它报出角色和配置版本号，对得上就算装好。

## 模型工具：安装、配置与第一次离线运行

依赖 Bash、Python 3、jq、GNU coreutils。下载仓库后直接运行 scripts/ 下的三个入口，无需安装到系统目录；如需加入 PATH，把整个 scripts 目录加入 PATH，保留两个共享文件。实际调用另需自己安装并认证对应 CLI；详细配置和兼容差异见 [scripts/CONFIG.md](scripts/CONFIG.md)。

复制 examples/runtime.json 和 examples/review-policy.json 到自己的配置目录，再按虚构团队示例修改路径、引擎命令、默认模型/强度和 agent 名单；设置 ORCHESTRA_CONFIG 指向自己的 runtime.json。配置不存密钥，认证由引擎或使用者环境提供。rules_file 指向配对表，routes 仍由人选择、传参，不自动派工。

以下在仓库根目录执行，不需要真实账号，不调用模型；临时目录在当前仓库内，最后可自行删除：

```bash
scripts/run-model --help
scripts/run-estimate --help
scripts/check-run --help
scratch=$(mktemp -d ./orchestra-offline.XXXXXX)
cp examples/runs.jsonl examples/output.txt "$scratch/"
scripts/run-estimate --engine claude --file "$scratch/runs.jsonl"
scripts/check-run --file "$scratch/runs.jsonl" --recent 3
scripts/check-run --file "$scratch/runs.jsonl" demo-001
```

预期估时中位数为 40 秒，核对输出含 `OK: output exists`。实际运行时指定 --engine、--agent、--task 和提示词，使用 --role code|review、--work-id 把同一工作关联起来；其余参数见 --help。run-model 的 --commit 会实际暂存和提交，只在明确授权后使用。

## 新增或修改技能：PR 流程（Change Workflow）

几个词：分支是 PR 里那份草稿副本；分支保护是 GitHub 上的开关，规定 `main` 只能经 PR 改、不许强推（force push）；CI 是每次提 PR 时自动跑的检查。

流程：

1. 你或任何助手提出，记一条待办。
2. 你同意后，由配置管理角色开分支改文件、开 PR（推送和开 PR 要你同意，可一起批），写清改什么、为什么、影响谁。
3. CI 跑格式检查。
4. 你看过全文、批准，合并。
5. 由调度角色同步，改写受影响的设定。
6. 对应仓库的 `CHANGELOG.md` 加一条、版本号 +1，群里发全文；抽查时让助手报配置版本号，对不上就是没同步。

### 分支保护与 CI（Branch Protection & CI）

- 两个仓库同样配：**必须走 PR、禁止强推、格式检查通过才能合并**。
- 要勾「管理员也不许绕过」，因为助手们可能用的是你的账号。
- 个人账号的私有仓库，免费版可能开不了分支保护（凭记忆，待核实）。自查：仓库 Settings → Branches 加一条规则，提示要升级就是开不了。开不了时：通用仓库公开后免费就能开；配置仓库升级付费版，或者 CI 照跑、靠规矩「红了不合并」、同步脚本再查一遍。

CI 格式检查查四样：

1. 表格文件读得了、规则表必填项齐；
2. `SKILL.md` 开头齐全、提到的文件都在；
3. 通用部分没有禁用词；
4. 没有像密钥的字符串和本机路径。

禁用词清单本身是隐私，CI 从 GitHub 的加密变量（只有仓库主人能看的机密设置）里读。CI 碰不到你的电脑，同步仍靠同步脚本。

## 同步方式（How Sync Works）

正本是唯一以它为准的那份。本仓库的 `main` 是通用部分的正本；你的私有配置仓库的 `main` 是配置的正本。本机技能目录、模型调用程序读取的规则表、各助手的线上设定都是抄本，只从正本复制。

合并后由调度角色跑同步脚本：**检查 → 备份 → 复制**，由使用者确认；受影响的线上设定由调度角色全文写入，使用者确认；先检查，不过不装；先备份；只装已合并的内容；装完在群里发改动全文。

| 内容 | 正本 | 抄本（本机） | 谁同步 |
|---|---|---|---|
| 技能文件 | 本仓库的 `main` | 技能目录下的 `orchestra/` | 调度角色，每次合并后跑同步脚本 |
| 你的配置 | 你的私有配置仓库的 `main` | 同一文件夹里的 `config/` | 同上 |
| 规则表 | `config/rules.json` | 模型调用程序只读的本机规则表（TODO：确认同步目标路径） | 同上 |
| 线上设定 | `config/profiles/` | 各助手的线上设定 | 调度角色全文写入，使用者确认 |
| 模型调用程序代码 | 本仓库 scripts/ | 使用者选择的工具目录 | 开发角色维护，安装前备份并验证 |

### 助手设定怎么管（Assistant Profiles）

- 正本放私有配置仓库的 `config/profiles/`。
- 线上设定（profile）只留身份、权限底线和「开工先读技能」，具体流程写进技能。
- 用冒烟测试确认助手真会读技能（装好后跑一次最简单的试用）。
- 线上设定只能全文写入；不许直接改，写入前先比对，不一样先问。
- **新增助手的配置与验收：** ① 配置管理角色在 `config/team.json` 加一行（名字、角色、能用的引擎），照 `roles/` 的模板、填上 `team.json` 里的名字，写出该助手的设定全文；② 走上面的 PR 流程，使用者批准后才合并；③ 合并后由调度角色跑同步脚本，把设定全文写进它的线上设定；④ 让它报出角色和配置版本号，对得上就算装好。

### 防走样（Drift Prevention）

- 调度角色每天比对规则表的抄本和正本。
- 出问题先恢复备份，再走 PR 修。
- 规则表格式要变时，先装能读新表的模型调用程序，再换表。

## 隐私边界（Privacy Boundary）

- **密钥、令牌、登录文件：哪个仓库都不进，私有的也不进。**
- 你的名字、助手名单、项目名、账号名、私有仓库名、本机路径、模型账号档位、待办和群的信息：只进你的私有配置仓库；通用说明里的仓库地址写成〈仓库地址〉。
- 角色、流程、模板、格式说明、虚构示例：可以给别人。
- 挡泄露：本仓库 `.gitignore` 写上 `config/`；CI 查禁用词和密钥；`examples/` 只用虚构团队。
- 历史遗留：旧版本里若有隐私内容，改掉后仍留在历史里。只发导出包没事；要公开或邀请人，得先清历史（要强推，需你批准），或另建干净仓库。
- 个人配置放在你自己的私有仓库，不进本仓库。

## 贡献规则（Contributing）

- 改动一律走 PR：从 `main` 开分支，写清改什么、为什么、影响谁；CI 格式检查通过、仓库主人看过全文并批准后才能合并。
- 禁止直接改 `main`，禁止强推。
- 复审不用作者用过的那家模型；不合并自己的改动。
- 改规矩按 `process/change-rules.md` 走上面的 PR 流程。
- 合并后更新 `CHANGELOG.md`、版本号 +1，并由调度角色同步到本机。
- 新增角色/流程/模板时，放进对应目录（`roles/`、`process/`、`routing/`）；`SKILL.md` 只写一页，细节放子文件，用到才读。
