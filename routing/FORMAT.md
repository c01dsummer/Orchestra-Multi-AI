# 规则表格式说明（格式版本 1）

规则表是一个 JSON 文件（程序能直接读的表格文本），管两件事：

1. **跨家复审配对**（必填）：哪家引擎写的代码，可以交给哪几家引擎复审。
2. **任务路由**（可选）：什么活用哪个引擎、哪个模型、多大强度，失败了换谁。

先说几个词：

- **引擎**：某一家的模型服务。同一家的不同模型算同一个引擎。
- **作者引擎**：给某项工作写过代码的引擎。
- **复审引擎**：检查别人写的代码的引擎。
- **工作编号**：把属于同一项工作的多次运行串起来的编号。
- **包装程序**（wrapper）：替助手调用模型、并把每次运行记进运行记录的程序。它不随本技能分发。没有它的，这张表就当选模型的参考；第五节写的检查可以人工照做，也可以照着自己写一个同类程序。本说明里的「现有包装程序」，指现有的、替助手调用模型引擎并记录每次运行的命令行包装脚本。
- **JSON 写法**：`{}` 是对象（一组「键: 值」），`[]` 是数组（有先后的列表），`"…"` 是字符串（一段文字）。

## 一、放在哪、谁来改

- **正本**：配置里的 `config/rules.json`，唯一以它为准的一份。要改，走改规矩的流程。
- **抄本**：包装程序读的那一份，位置由包装程序自己定。只能从正本同步过去，不要直接改。
- **空白模板**：`routing/template.rules.json`。复制成 `config/rules.json`，把所有〈…〉换成你自己的值（〈〉表示留给使用者填的空），用不到的可选字段整段删掉。引擎有几家就写几家，模板里的三家只是示例。

## 二、整个文件的要求

- 严格的 JSON：UTF-8 编码，不带 BOM（有的读表程序不认）；不能写注释，不能有多余的结尾逗号，不能用 NaN、Infinity。
- 整个文件只有一个 JSON 对象，最外层是一对 `{}`。
- 同一层里不能有重名的键。
- 字段名区分大小写，照本说明写。
- 不写密钥、令牌、本机路径。

## 三、字段一览

| 字段 | 类型 | 必填 | 管什么 | 现有包装程序 |
|---|---|---|---|---|
| `version` | 整数 | 必填 | 格式版本号，现在是 1 | 读，只在复审检查时读：不等于 1 就拒绝复审 |
| `name` | 字符串 | 可选，建议写 | 表的标题 | 不读 |
| `description` | 字符串 | 可选，建议写 | 写给人看的说明 | 不读 |
| `reviewers` | 对象 | 必填 | 跨家复审配对 | 读，只在复审检查时读 |
| `routes` | 对象 | 可选 | 按任务类型选引擎、模型、强度，以及失败了换谁 | 不读，整段忽略 |

`version`、`name`、`description`、`reviewers` 是格式版本 1 原有的字段，含义不变。`routes` 是定稿时新增的可选字段，没有它的表照样合格。

除了这五个，不要自己加字段。现有包装程序会忽略不认识的字段，但别的读表方不知道它是什么意思。要加，走改规矩的流程，并按第六节判断要不要升版本。

## 四、逐个字段

### 4.1 `version`（必填）

- 类型：整数。按本说明写的表一律写 `1`。
- 含义：这张表照哪一版格式写。它**不是**配置内容的版本号：只改表的内容（增删引擎、改列表、加路由），`version` 不变，改动记进配置自己的改动记录（CHANGELOG）。
- 现有包装程序：复审检查时读，`version` 不等于 1（缺了、写成字符串 `"1"` 都算）就拒绝复审（退出码 2），不猜着读，见第五节第 1 步。不检查 `version` 的旧程序（比如更早版本的包装程序），光改这个数拦不住，见第六节。

### 4.2 `name`、`description`（可选，建议写）

- 类型：字符串；写了就不要留空。
- 含义：表的标题和说明，给人看。`description` 建议用一两句话写清 `reviewers` 怎么读，方便没看过本说明的人。
- 现有包装程序：不读。

### 4.3 `reviewers`（必填）

每个键是一个作者引擎，值是「可以复审这家写的代码的引擎」列表：

```json
"reviewers": {
  "〈引擎A〉": ["〈引擎B〉", "〈引擎C〉"],
  "〈引擎B〉": ["〈引擎A〉", "〈引擎C〉"],
  "〈引擎C〉": ["〈引擎A〉", "〈引擎B〉"]
}
```

取值约束：

1. `reviewers` 是对象，至少有一个键。
2. 每个值是数组，至少一项；每一项是非空字符串，也就是一个引擎名。值不能写成字符串或对象：现有包装程序复审时先查整张表，哪个值不是至少一项的数组，或者里面有一项不是非空、不含空白的字符串，就拒绝复审（退出码 2），哪怕这个键这次用不到（见第五节第 1 步）。
3. 引擎名必须和包装程序选引擎用的名字（`--engine` 的取值）一字不差，区分大小写。整张表和团队名单里，同一个引擎的写法要一致。
4. 列表里不能有键自己。自己复审自己不算复审，包装程序也一律拒绝。
5. 列表里不要重复。列表的先后没有意义，包装程序只看「在不在」；想写「优先找谁复审」，写在 `routes` 里。
6. 配对是单向的：〈引擎A〉的列表里有〈引擎B〉，不等于〈引擎B〉的列表里有〈引擎A〉，要各写各的。
7. 会写代码、写完要复审的引擎，都必须作为键写进来。不在键里的作者引擎，包装程序当它的列表是空的，这项工作谁都不能复审。
8. 只复审、不写代码的引擎，可以只出现在列表里，不当键。
9. 至少要有两家引擎，跨家复审才成立。
10. 以引擎为单位，不分模型：作者用过某一家的任何一个模型，这一家就不能复审这项工作。

一项工作有好几家写过代码时，复审引擎不能是其中任何一家，还必须同时出现在每一家作者引擎的列表里。拿上面的表举例：只有〈引擎A〉写过，〈引擎B〉〈引擎C〉都能复审；〈引擎A〉〈引擎B〉都写过，只剩〈引擎C〉；三家都写过，就没有引擎能复审，包装程序会拒绝复审运行，要请使用者定怎么处理。

现有包装程序怎么用它：见第五节。

### 4.4 `routes`（可选）

```json
"routes": {
  "〈任务类型A〉": {
    "description": "〈什么样的活算这一类；有专门规定也写在这里〉",
    "candidates": [
      { "engine": "〈引擎A〉", "model": "〈模型名〉", "effort": "〈强度〉" },
      { "engine": "〈引擎B〉" }
    ]
  }
}
```

| 位置 | 类型 | 必填 | 含义和约束 |
|---|---|---|---|
| `routes` | 对象 | 可选 | 键是任务类型名，自己起，非空字符串（比如「写代码」「复审」「调研」）；值是这一类活的路由 |
| `routes.〈任务类型〉.description` | 字符串 | 可选 | 什么样的活算这一类；这一类另有专门规定的（见下面第 8 条），也写在这里，或者写明去哪份流程看，这时就必须写；写了就不要留空 |
| `routes.〈任务类型〉.candidates` | 数组 | 写了这一类就必填，至少一项 | 候选，按顺序排：第一项是首选，后面依次是失败时的替补 |
| 候选里的 `engine` | 字符串 | 必填 | 引擎名，写法同 `reviewers` |
| 候选里的 `model` | 字符串 | 可选 | 模型名；不写就用这个引擎的默认模型 |
| 候选里的 `effort` | 字符串 | 可选 | 推理强度；不写就用默认；引擎不支持强度就不要写（有的调用程序会直接拒绝） |

`model`、`effort` 能填哪些值，取决于引擎和调用程序，本说明不列，照你用的工具写。同一个引擎可以出现在好几项里，比如先用高强度，失败了再换低强度。

怎么选、怎么替补（某一类写了专门规定的，先看第 8 条）：

1. 按任务类型找到对应的一项。表里没有这类活，就是表对它不作要求，照别的规矩办；拿不准就问使用者，不要猜。
2. 从第一个候选开始。复审类的活，先跳过 `reviewers` 不允许的候选（作者引擎本身，以及不在每一家作者引擎列表里的引擎）；跳过不算失败。
3. 失败了才换下一个。失败指：运行的退出码不是 0；跑完没有可用的产出；或者引擎调不起来（没登录、额度用完、服务不可用）。这里说的失败都是运行失败。
4. 下面三种不算失败，不能借机换下一个：
   - 调用程序因为参数不对、或复审检查不过而拒绝运行：说明表写错了或候选选错了，先改正，并告诉使用者；
   - 复审意见不合心意：不能靠换一家来换个结论；
   - 质量不过：产出能用，但没通过把关（复审没过、测试没过、结果被打回）。这和运行失败是两回事。要不要修、谁来修、要不要换一家重做，照这一类的专门规定（第 8 条）；没有规定就报告使用者。
5. 每个候选最多用一次。
6. 候选都用完了还不成，就停下来报告使用者，不要自己用表外的引擎。
7. 写代码的活换了引擎，失败的那家也算作者：包装程序把同一工作编号下所有写代码的运行都算上，不管成败。作者越多，能复审的引擎越少，可能一家都不剩。
8. 专门规定优先。某一类在 `description` 里写了专门规定，就先照它办，第 2–7 条只管它没说到的情况。专门规定可以写：这一类只在什么日期、什么风险等级适用；什么情况才换下一个（比如只有某几种失败才换，换之前先报告、等人安排）；质量不过怎么修、修几次；等多久、找谁批；每次用之前要先查什么。专门规定也不能越过 `reviewers`，不能用表外的引擎。它和 `routes` 一样是写给人看的，程序不读、不强制。里面还没定的地方要写明没定，遇到了问使用者，不要猜。

和 `reviewers` 的关系：`reviewers` 是硬规定，由包装程序强制执行；`routes` 是建议，靠助手照着做。两者冲突时以 `reviewers` 为准。

现有包装程序：不读 `routes`，整段忽略。引擎、模型、强度由助手照表自己传给包装程序（`--engine`、`--model`、`--effort`）。

## 五、现有包装程序怎么用这张表

包装程序只读 `version` 和 `reviewers` 两个字段（另外要求整个文件恰好是一个 JSON 对象），其余字段一概不看。

**什么时候读**

- 只在同时给了 `--role review`（复审）和 `--work-id`（工作编号）时读。
- `--work-id` 每次运行都必填，复审、写代码都一样：没给，或者不合包装程序规定的编号格式，在读表之前就拒绝运行（退出码 2），不调用引擎，也不记进运行记录。
- `--role` 也必填，只收 `code`（写代码，要复审的文档、配置也算）和 `review`：`--role code` 的运行不读表；不给 `--role`，或者写成别的值（比如 `other`），在读表之前就拒绝运行（退出码 2）。

**读了怎么判断**

1. 先查整张表，下面任何一处不对，就拒绝运行（退出码 2）：文件不存在、读不了或者不是合法 JSON；文件里不是恰好一个 JSON 值，或者这个值不是对象；`version` 不等于 1；`reviewers` 缺了、不是对象，或者是空对象 `{}`；`reviewers` 的某个键不是引擎名；某个值不是至少一项的数组，或者里面有一项不是引擎名。这一步说的引擎名只看写法：非空、不含空白的字符串；是不是真有这个引擎、列表里有没有键自己、有没有重复，这一步都不查。查的是整张表，不只是这项工作用得到的键，而且在查运行记录之前：所以抄本有任何一处这样的毛病，所有复审都会被拒，哪怕这项工作还没有作者运行。
2. 查运行记录：同一工作编号下、没记为 `--role review` 的所有运行（下称作者运行：`--role code` 的，以及记录里 role 是别的值或没有 role 的），不管成败，用过的引擎都算作者引擎。运行记录存在但读不了，也拒绝运行；记录里读不成 JSON 的行会被跳过，不报错。
3. 一次作者运行都没找到：只警告（可能是工作编号写错了），不检查，照常运行。
4. 算出允许的复审引擎：在表里某个列表中出现过、不是任何一家作者引擎、并且在每一家作者引擎的列表里。
5. 本次的 `--engine` 是作者引擎之一，或者不在允许名单里，就拒绝运行（退出码 2）；报错里会列出作者运行和允许的复审引擎。作者运行里有没记引擎的（缺了、空的或者不是字符串），认不出作者引擎，也拒绝运行（退出码 2）。第 4、5 步比引擎名，都是整个名字一字不差地比（区分大小写），不按包含关系算。

**几个直接后果**

- 作者引擎不在 `reviewers` 的键里：它的列表按空算，这项工作没人能复审。
- `reviewers` 是空对象 `{}`：第 1 步就拒绝，和缺了 `reviewers` 一样，不管这项工作有没有作者运行。
- 抄本里还留着〈引擎A〉这类占位：占位的写法能过第 1 步；找到了作者运行时，真实引擎名一个都对不上，复审被拒；找不到作者运行，只警告、照常运行，占位拦不住。
- 只有作者配对检查（第 4、5 步）是在找到作者运行时才拦人：编号写错（格式对，但不是这项工作的编号）、作者运行没带编号，或者那几行记录读不成 JSON，都只是警告或被跳过。所以包装程序放行、自动检查（CI）通过，都不证明作者记录齐全；复审前要自己核对工作编号和作者运行。规则表缺失或损坏（第 1 步那几种毛病）不一样：带工作编号的复审，哪怕这项工作还没有作者运行，也会在第一道检查就被拒。
- 包装程序只比 `--engine`，不比 `--model`：同一家换个模型来复审，照样算自己复审自己。

## 六、版本升级规则

1. `version` 是格式版本，和配置内容的版本号是两回事。只改表的内容，`version` 不变，改动记进配置的改动记录。
2. 升不升，看会不会读错：旧的读表程序读新表，或者新的读表程序读旧表，会不会理解错、放行不该放行的事。会，`version` 加 1；不会，不升。
   - 不用升的例子：新增一个可选字段，而且旧程序忽略它也不会放行表本意禁止的事（`routes` 就是这样：它只是建议，不放宽也不收紧复审检查）；把只给人看的字段（`name`、`description`）改成必填。
   - 要升的例子：删字段、改字段名、改已有字段的类型或含义；新增一个「旧程序忽略它，就会放行不该放行的事」的字段（比如另外禁止某些配对）。
3. 升版本的顺序：先装能读新版本的包装程序（最好新旧两版都能读），每家引擎都试跑通过，再换表。
4. 现有包装程序复审时检查 `version`，不等于 1 就拒绝，不猜着读；但不检查 `version` 的旧程序（比如更早版本的包装程序），光改这个数拦不住它们。所以 `reviewers` 的含义永远不改；要换含义，就起一个新的字段名，过渡期新旧并存。这样旧程序要么照旧含义读，要么读不到 `reviewers` 而拒绝复审：宁可拒绝，不能读错。
5. 以后的读表程序遇到不认识的 `version`，要拒绝，不要猜着读。
6. 凡是改格式（升不升版本都算）：本说明、空白模板、示例和自动检查（CI）里的必填字段清单，在同一次改动里一起改，记进通用部分的改动记录；正本 `config/rules.json` 需要补的同时补上，记进配置的改动记录。

## 七、改表自检清单

提交改动前逐条看：

- [ ] 是合法 JSON，最外层是对象，没有注释和结尾逗号；
- [ ] `version` 是整数 `1`；
- [ ] `reviewers` 是对象；每个值是非空数组，每一项是非空字符串；
- [ ] 引擎名和包装程序的 `--engine` 取值一致，没有留下〈…〉；
- [ ] 每个列表不含键自己，没有重复；
- [ ] 会写代码的引擎都作为键写了；
- [ ] 写了 `routes` 的话：每一类都有非空的 `candidates`，每个候选都有 `engine`，引擎名写法同 `reviewers`，不支持强度的引擎没写 `effort`；有专门规定的类，规定写进了 `description`（或写明去哪看），没定的地方写明了没定；
- [ ] 没有密钥、令牌、本机路径。

自动检查（CI）只能查必填项在不在、空不空。类型（比如 `reviewers` 写成了数组，列表项写成了数字或 true/false）、取值（比如 `version` 写成 0）、键（比如作者引擎写成空字符串）、引擎名对不对、可选字段里面写得对不对，它都查不出来；文件带 BOM、同一层有重名的键，它也不报。这些要靠这张清单和复审。

本地运行 `bash scripts/check.sh` 还会严格检查编码、重复键、版本和字段类型、非空引擎、自审、重复配对及路由候选，并核对示例或本地团队的引擎列表。只有空白模板允许占位符；示例和本地规则表必须全部替换。真实引擎与模型是否可调用、作者记录是否齐全、路由专门规定是否执行，仍需使用者的工具与跨家复审确认。
